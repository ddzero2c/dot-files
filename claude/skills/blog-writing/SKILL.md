# Blog Writing

用繁體中文（zh-TW）寫作，technical terms 一律保留英文原文（不要翻成「快取」、「編譯器」這種中譯，直接寫 cache、compiler）。語氣是一個工程師在跟同行講話：白話、第一人稱、先給證據、大方給 credit、對自己的錯誤誠實。

## 先決定文章形狀

| 形狀 | 用在 | 結構 |
|---|---|---|
| Announcement | 消息：release、捐款、決定 | 第一句就把消息說完。接著講個人的「為什麼」。短。 |
| Technical deep-dive | 某個東西怎麼運作／怎麼修好的 | 像目錄一樣的 `##` 標題、逐層加深（「X 的解剖」、「先從最簡單的情況開始」）、真的 code 與原始輸出、「小結」段落 |
| Essay / opinion | 一個想法或立場 | 少標題或不用標題；用一句反覆出現的話當骨幹；結尾收在一句格言 |
| Devlog | 專案定期更新 | 固定儀式：打招呼 → 社群動態 → 功能標成 `名稱 (#PR)` → 「收工」→ 致謝 → 署名 |
| Postmortem | 一個 bug 的故事 | 偵探敘事：症狀 → 錯誤的猜測（要留著！）→ 真正的原因 → 修法 → 學到什麼 |

## 開頭

第一句就把消息或主題平鋪直述講完。不要清喉嚨，不要「本文將介紹」，不要故事鉤子或修辭暖場。

- 「我們把 build cache open source 了，它叫 Forge。」
- 「接下來一年，我們會全額資助 parser 專案的兩位 full-time maintainer。」
- 「SIMD 一直有個難的名聲。」（先點名你接下來要打破的誤解）
- 或者直接叫讀者動手：「在 shell 裡對一個空檔案跑 `wc -c`。再把同一個檔案用 pipe 餵進去跑一次。答案不一樣？」

第二句要重複主詞名詞、而不是用代名詞，是可以的（「Tokenization 是……Tokenization 是……」）——清楚優先於漂亮。

## 語氣規則

- 第一人稱，一直用，而且不用道歉：「我認為」、「我建議」、「這個決定我一點都不後悔」。不要躲在被動語態或「一般來說會」後面。
- 節奏交替：長的解釋句之後，接一個很短的反應句——「完蛋。」「不錯。」「有趣。」「唉。」短句是拍點，不是填充。
- 用重複來加重：重要的話講三次（「cache 是冷的。cache 一直都是冷的。」）。讓一個你自己造的短語貫串全文當骨幹（「小、無聊、正確」、「queue 就是 queue 就是 queue」）。
- 幽默要乾、要短、要自嘲，常常放在括號或 footnote 裡——「（呃，這種錯我沒再犯第二次）」。不要演。
- 刻意造詞並定義：「這裡我用『Blind Prompting』來指……」。jargon 先定義再用。
- 口語轉折句：「我們來看看……」、「話說回來……」、「結果是……」、「講白一點就是……」、「所以呢，……」。句子可以用「而且」、「但是」、「好，」開頭。
- 數字就是證據，要精確不要湊整：「6 天後 22 GB」、「token 花了 $8.41」、「大約 3,000 行」。
- 真的有情緒時可以寫出來（「我愛這個 database 愛到有點不正常，而我現在很氣它」）——但下一句馬上落回具體事實。

## 主張、保留、反駁

- 意見講得斬釘截鐵，然後在同一口氣裡限縮範圍：「它不完美、還沒做完、也不適合每個人。但它是我的。」／「這對你可能沒用。」
- 先幫對方把反對意見講清楚：「應該會有人說……」、「當然，你可能會指出……」——然後收斂到真正的分歧點。絕不打稻草人。
- 敏感的主張要明講：「我想把話講清楚……」、「我再講一次，因為這是不太舒服的事實……」。
- 不懂就直說，不要糊過去：「我沒有硬數據支持這件事」、「我不想假裝我在這題上很權威，所以我跳過。」
- 沒有結論的爭論就收掉，不要糾纏：「我選了 Rust，我喜歡 Rust，往下走。」／「我不想引戰！」
- 替某個東西辯護時，附一個誠實的「缺點」段落：「為了誠實，我把我想得到的都列出來。」
- 自己的錯就平淡認一次，然後往前走。postmortem 裡錯誤的猜測要留著——那條錯路就是故事本身。

## 結構機制

- `##` 標題要讀起來像論證的推進，不是索引標籤：「房間裡的大象」、「不好的部分」、「為什麼要第二個 scheduler？」、「Step 1……Step 6」。
- Footnote 是第二個聲音——更乾、更好笑、更保留。用來放旁話、免責、利益揭露、笑話（「YAML。😐」）。它們有實際作用，不只是引用。
- 展示真的東西：確切的檔案路徑、確切的指令、原封不動貼上的 benchmark 輸出——然後才用文字解讀。證據在前，敘述在後。歡迎讀者自己驗證。
- 複雜度分層：從最簡單的例子開始往上疊；長段技術內容之後做小結（「我們把實作對回前面那五個步驟」）。每節結尾留一句短的收尾。
- primary source 直接 inline 連結（PR、talk、文章），不要做參考文獻列表。長技術文加目錄。
- 長度跟著企圖心：一個想法的散文 400 字就夠，internals 導覽可以 5,000 字。不要灌水，也不要硬砍。
- 把自己的範圍講出來：「這篇不會教你 Rust 或 GPU programming。」／「我不會細講這個 algorithm 怎麼運作。」

## 結尾

低調、往前看、比正文更謙虛一點。絕不凱旋。

- 散文：把論點收成近乎格言的一句，有時就用標題本身當最後一句（「你得自己跑一次。」／「一點點 schema 就能撐很久。」）。
- 技術文：一個實用的指路、一句鼓勵，或交棒給系列下一篇——「下一篇：type checker。」／「希望這些細節能讓你更快找到答案。」
- Announcement：軟性的行動呼籲（「有能力的話，請考慮捐款。」）以及接下來會發生什麼。
- 指名道姓感謝。credit 是內容，不是裝飾。
- 對自己的未來留一手很符合這個聲音：「我確定我以後回頭看這篇會笑自己天真。」

## 透明度儀式

- 揭露利益與過程：錢、關係、文字有沒有經過 AI（「這篇全部手寫……我很討厭我得特別說這句。」）。
- 社群性的工作用「我們」，而且在專案不再是一個人做的時候明講這個轉變。
- 私人生活（小孩、家人）可以出現在技術文裡，不用道歉，但一個子句就好，不是一段。

## 反例（一出現就走味）

- 用反問句開場、「在這個變化飛快的時代……」、故事先行的鉤子。
- 吹捧形容詞（「顛覆」、「快到炸裂」、「blazingly」）、驚嘆號連發、行銷腔。
- 每句都在保留，或完全不保留；正確的模式是大膽的主張 → 一句誠實的範圍限縮。
- 大量粗體、emoji 撒滿（emoji 要單一、有位置、有語氣——一個固定的署名符號、或用 😐 當整個笑話）、清單體。
- 只總結證據而不展示證據。把本來可以精確的數字湊整。
- 跟想像中的批評者長篇對打；反對意見點一次、回一次、往下走。
- 把 technical terms 翻成中文（寫 cache 不寫「快取」，寫 commit 不寫「提交」）。

## 交稿前檢查清單

1. 第一句有沒有平鋪直述地講出消息／主題？
2. 是第一人稱、而且意見是自己的嗎？
3. 至少有一個原始呈現的真實物證（數字、code、指令、log）嗎？
4. 反對意見有沒有先被公平點名並限縮，而不是被硬打？
5. 旁話有放在 footnote，而不是塞在正文裡嗎？
6. 結尾比中段安靜，而且該謝的人有指名嗎？
7. 唸出來：短拍點有把長句斷開嗎？
8. technical terms 都保留英文了嗎？
